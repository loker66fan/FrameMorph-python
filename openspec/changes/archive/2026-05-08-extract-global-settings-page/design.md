## Context

当前应用已经把一级导航拆分为文档工作台和图片工作台，但“设置中心”仍然作为文档工作台内部的一个伪模块存在。这导致全局偏好设置和文档处理模块耦合，也让主题、字体大小和默认输出目录这类软件级配置缺少明确的生命周期与统一入口。

现有代码还没有正式的应用设置持久化层：主题切换、应用字体大小和默认输出目录都没有被定义为跨页面共享的全局配置。另一方面，`qfluentwidgets` 已经提供了主题 API、配置模型和设置卡片组件，因此适合在不引入新依赖的前提下建立统一设置页。

## Goals / Non-Goals

**Goals:**
- 将“设置中心”从文档工作台内部移出，改为左侧一级导航底部的独立设置页。
- 建立统一的应用级配置入口，至少覆盖默认输出目录、主题切换和软件字体大小。
- 让配置具备持久化能力，并在应用启动或主窗口初始化时生效。
- 让文档工作台和图片工作台都能消费统一设置，而不是各自维护局部默认值。

**Non-Goals:**
- 不在本次中引入 OCR 语言、缓存策略、并发数等更复杂的偏好系统。
- 不重做整个文档工作台的模块架构，重点仅限于移除内部设置模块并接入全局设置页。
- 不对图片编辑、文档处理或导出算法本身做行为修改。

## Decisions

### 1. 设置页作为独立一级页面注册到底部导航
在 `MainWindow` 中新增独立设置页，并使用 `addSubInterface(..., position=NavigationItemPosition.BOTTOM)` 放到左侧导航底部。

- Rationale: 设置属于全局应用能力，放到底部导航更符合桌面应用习惯，也能与业务工作台清晰分离。
- Alternative considered: 保留在文档工作台内部，仅增强现有“设置中心”。该方案会继续放大全局职责与模块职责的耦合，因此不采用。

### 2. 使用 qfluentwidgets 的 qconfig 与设置卡片建立配置层
使用现有 `qfluentwidgets` 提供的 `qconfig`、`ConfigItem` 和设置卡片组件组织偏好项，而不是自定义 JSON 存储格式。

- Rationale: 依赖已存在，且主题 API 与设置 UI 组件天然匹配，能够减少样板代码并保持 UI 风格统一。
- Alternative considered: 自建配置文件和表单。该方案灵活，但会重复框架已有能力。

### 3. 默认输出目录定义为全局应用设置
默认输出目录不只服务文档工作台，还作为软件级默认输出位置，为后续图片导出对话框默认目录预留统一来源。

- Rationale: 用户对“默认输出目录”的理解通常是软件级的，而不是模块级的。
- Alternative considered: 仅将其保留为文档工作台设置。该方案实现更小，但会削弱独立设置页的意义。

### 4. 字体大小首版采用有限档位而非任意数值
软件字体大小用少量预设档位表示，例如小/标准/大，而不是直接开放任意 point size。

- Rationale: 预设档位更容易验证布局稳定性，能降低 Fluent 界面在紧凑布局下被撑坏的风险。
- Alternative considered: 允许自由输入字号。该方案灵活，但验证成本更高。

### 5. 文档工作台仅保留依赖检测和输出目录消费逻辑
文档工作台中的“设置中心”模块从导航中移除；如需保留环境状态展示，应迁移到全局设置页或改为共享辅助区逻辑。

- Rationale: 文档工作台应聚焦任务处理，不继续承载全局设置职责。
- Alternative considered: 同时保留两个设置入口。该方案会造成配置入口重复和语义混乱。

## Risks / Trade-offs

- [设置持久化接入点不清晰] → 在 `main.py` 或主窗口初始化阶段集中应用主题和字体，避免页面各自决定配置生效时机。
- [默认输出目录语义扩展导致旧逻辑混乱] → 先统一配置来源，文档工作台优先接入，图片导出只改默认初始目录而不改保存行为。
- [字体大小影响现有紧凑布局] → 首版仅提供有限档位，并在主要页面验证导航、面板和列表布局。
- [设置页抽离后现有状态展示丢失] → 明确把依赖检测与输出目录展示迁移到新设置页，而不是直接删除。
