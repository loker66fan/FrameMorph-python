## Context

该仓库是一个基于 PySide6 的本地图像编辑桌面应用，当前代码、文档处理能力、模型资源和 Windows 离线构建资源都保存在同一仓库中。现状中最大的体积来源并非主程序源码，而是 `release/` 下的离线构建产物与 wheelhouse，以及运行时 `requirements.txt` 同时承担桌面编辑和文档处理场景，导致默认安装路径偏重。

本次变更要求功能保持不变，因此重点不是删除用户可见能力，而是重新划分运行时与发布时边界，并在现有模块内做等价简化。变更需要兼顾三个约束：桌面应用仍可正常启动；文档相关能力仍然可用；Windows 便携构建流程仍然可维护。

## Goals / Non-Goals

**Goals:**
- 将默认运行时依赖控制在实际应用启动和核心功能所需范围内。
- 将大型离线构建资源从默认开发/运行路径中隔离，降低仓库日常使用体积感知。
- 清理可确认未使用、重复或可内联简化的实现，降低模块复杂度。
- 保证现有图像编辑、文档处理、增强预览和导出行为不发生用户可见变化。

**Non-Goals:**
- 不新增任何用户功能或 UI 流程。
- 不替换当前技术栈，不引入新的外部服务或打包系统。
- 不追求删除现有发布能力，只调整其组织方式和默认依赖路径。
- 不对图像处理算法或导出结果做行为性修改。

## Decisions

### 1. 运行时依赖与构建依赖分离
将 `requirements.txt` 收敛为应用运行必需依赖，把仅用于离线打包、平台构建或可选场景的内容迁移到专用依赖清单或现有发布目录中引用。

- Rationale: 默认安装路径应优先服务开发和运行，而不是携带构建场景的全部负担。
- Alternative considered: 保持单一依赖文件，只在文档中说明差异。该方案对仓库使用者没有实际减负效果，因此不采用。

### 2. 发布大文件继续保留能力，但从日常项目主路径弱化
保留 Windows 离线构建能力和现有发布资源语义，但通过文档、目录职责和任务拆分，把它们视为发布工件而非常规开发输入。

- Rationale: 这些资源体积大，但对发布仍有价值，直接删除会破坏现有流程。
- Alternative considered: 完全移除离线资源并改为在线下载。该方案会改变离线构建能力，不满足“功能不变”。

### 3. 代码优化以“等价简化”为边界
只处理可证明不改变行为的优化，例如删除未使用代码、合并重复逻辑、收敛导入和职责边界，不进行跨模块的大规模重写。

- Rationale: 用户要求保持功能不变，局部等价简化更容易验证。
- Alternative considered: 进行全面架构重构。该方案收益不确定，验证成本高，超出本次范围。

### 4. 文档处理能力作为保留能力显式校验
由于仓库已包含 `PyMuPDF`、`pypdf`、`python-docx` 和文档相关模块，本次优化中必须把文档处理流程纳入保留范围，而不是仅按图像编辑主路径裁剪依赖。

- Rationale: 这部分能力已经存在于当前项目，裁剪时若忽略会造成隐性功能回退。
- Alternative considered: 将文档能力视为次要功能并延后处理。该方案无法保证“功能不变”。

## Risks / Trade-offs

- [依赖裁剪误伤次要功能] → 在落地前逐项核对导入来源，并验证图像编辑、文档处理、导出与打包说明是否仍闭环。
- [发布资源调整引发构建说明失真] → 同步更新打包文档和发布目录说明，保持离线构建入口不变或给出明确迁移路径。
- [代码清理范围失控] → 只接受可直接证明等价的局部简化，避免顺手扩展成重构项目。
- [仓库体积主要来自发布资源，代码优化收益有限] → 将“默认路径减负”和“源码简化”同时作为目标，而不是只押注某一侧。
